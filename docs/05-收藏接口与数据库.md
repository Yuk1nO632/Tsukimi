## 先观察结果

按根目录 README 启动前后端，在同一个浏览器访问 http://127.0.0.1:3000：

1. 收藏一部番剧，观察卡片、顶部数量和“我的追番”。
2. 完整刷新页面，等待读取完成，收藏仍然存在。
3. 停止后端，再启动同一个后端，刷新页面，收藏仍然存在。
4. 取消收藏再刷新，记录也保持取消。
5. 换另一个浏览器或独立隐私窗口，应看到另一份片单。

开发时有两个进程：Next.js 提供页面和 API 转发，FastAPI 处理收藏读写。SQLite 是一个文件，不需要再启动第三个数据库服务器。当前机器依赖已安装，平时只需两个启动命令。

## 刷新为什么不再丢收藏

刷新仍会让 React state 重新初始化。变化在于：页面初始化后会请求后端，把数据库保存的收藏重新读回 state。

```text
第一次打开：
浏览器 GET /api/favorites
  → Next.js 转发到 FastAPI
  → 后端建立匿名会话，并通过 Set-Cookie 交给浏览器保存
  → 后端读取 SQLite 收藏，返回 JSON
  → React 把返回的 ID 写进 state，渲染按钮和数量

点击收藏：
浏览器 PUT /api/favorites/bgm-568244（自动携带 Cookie）
  → FastAPI 找到这份匿名会话
  → SQLite 写入收藏并提交
  → 后端返回已确认的收藏列表
  → React 更新 state

刷新：
state 先初始化 → 浏览器携带原 Cookie 请求 GET → 从 SQLite 恢复收藏
```

番剧卡片仍由本地片单生成，不会因打开页面就请求 Bangumi。浏览器本轮新增的联网请求是我们自己的收藏接口。

## 四种东西各自负责什么

| 内容 | 保存在何处 | 作用 |
| --- | --- | --- |
| React state | 当前页面的浏览器内存 | 决定按钮、计数和片单如何显示 |
| 匿名 Cookie | 当前浏览器 | 让后端识别这是哪份片单，不保存收藏列表本身 |
| SQLite 数据库 | project/backend/data/tsukimi.db | 保存会话与收藏关系，进程退出后文件仍在 |
| 番剧 JSON | project/catalog/catalog.json | 保存九部番剧的公开资料，供前后端共用 |

Cookie 使用随机值，数据库保存它的摘要。HttpOnly 表示页面 JavaScript 不能直接读取它，浏览器仍会在匹配的请求中自动携带。Cookie 自首次建立会话起有效 30 天；会话过期、清除 Cookie 或更换浏览器后，目前没有账号帮助找回原片单。

同一浏览器访问 127.0.0.1 和 localhost 时，Cookie 的主机不同，请固定使用 README 中的 127.0.0.1。其他已打开的标签页需刷新，才会重新读取最新收藏。

## 在 Network 面板看请求

打开浏览器开发者工具，在 Network 中筛选 favorites：

| 操作 | 请求 | 成功响应 |
| --- | --- | --- |
| 初始化或完整刷新 | GET /api/favorites | 当前浏览器的收藏 ID |
| 收藏 | PUT /api/favorites/{anime_id} | 保存后的收藏 ID |
| 取消 | DELETE /api/favorites/{anime_id} | 取消后的收藏 ID |

示例 JSON：

```json
{"favorite_ids": ["bgm-568244"]}
```

注意 Response、Status 和 Request Method，不只观察页面是否变了。Cookie 可以在浏览器存储面板中查看；无需复制或发送 Cookie 的具体值。

页面请求的是 3000 端口上的 /api，Next.js 根据 next.config.mjs 转发到 8000 端口，所以浏览器看到的是同源请求。这里没有额外配置 CORS；直接从浏览器访问不同端口的接口属于另一种联调方式，以后可以单独实验。

## 对照代码的顺序

1. frontend/components/favorite-button.jsx：点击按钮，调用 toggleFavorite。
2. frontend/components/collection-provider.jsx：管理显示状态；初次读取，等待写入确认后更新 state。
3. frontend/lib/collection-api.js：fetch 请求、超时、响应校验和错误消息。
4. frontend/next.config.mjs：/api 转发。
5. backend/main.py：GET、PUT、DELETE 路由，以及 Cookie 和会话。
6. backend/database.py：建表、SQL 查询、提交和关闭连接。

sessions 表保存匿名会话摘要与过期时间；favorites 表以“会话 + 番剧 ID”为联合主键。重复收藏不会插入重复行，取消时只操作当前会话的记录。SQL 参数与语句分开传入。

## 失败时会发生什么

- 初始读取中：按钮暂不可用，数量显示为待确认状态。
- 初始读取失败：显示“重新读取收藏”，不会把读取失败当成“没有收藏”。
- 保存中：禁用收藏按钮，防止连续点击产生冲突。
- 保存失败：保留上一次后端确认的收藏，不提示保存成功。
- 后端恢复：重新读取可恢复记录，再继续操作。
- 会话失效：写入返回 401，提示重新读取；未收录条目返回 404。

API 返回 Cache-Control: no-store，避免缓存把另一份状态当成最新收藏。当前还没有视频、播放进度、账号或跨设备同步。

## 测试和数据位置

后端在 backend 中运行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m unittest -v
```

八项测试覆盖进程重新创建后数据保留、不同会话隔离、PUT/DELETE 重复调用、Cookie、无效和过期会话、无效番剧、来源校验与数据库故障响应。测试用临时数据库，不修改你的片单。

本轮浏览器检查额外覆盖实际后端停止与重启、读取失败重试、保存失败不改变状态、连点保护、跨页面一致性与手机布局。前端生产构建也通过。

开发者本轮浏览器联调用的是 output 下的独立测试数据库；你正常启动后会创建自己的 backend/data/tsukimi.db。数据库、Cookie、虚拟环境和测试输出都不进入 Git。

## 资料同步的变化

同步命令仍是 frontend 中的 npm.cmd run sync:catalog。输出从之前的 catalog.generated.js 改为共用的 catalog/catalog.json，避免前后端维护两份 ID。后端启动时读取片单，所以同步后重启后端；Next.js 开发模式会读取更新，生产环境需重新构建前端。
