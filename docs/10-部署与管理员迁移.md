## A 一次访问经过哪些地方

### 页面与接口

```text
DNS 将 tsukimi.cc 解析到服务器公网 IPv4

浏览器访问 https://tsukimi.cc
    ↓ TCP 443、TLS 加密连接
腾讯云香港服务器上的 Nginx
    ├─ 页面和静态资源 → 127.0.0.1:3000 → Next.js
    └─ /api/ 请求    → 127.0.0.1:8000 → FastAPI → SQLite
```

例如浏览器请求 `https://tsukimi.cc/api/progress`，Nginx 按路径将它交给 FastAPI。FastAPI 根据 Cookie 找到账号，查询数据库，再返回 JSON。浏览器内的 React 用结果更新 state，重新显示继续观看卡片。

浏览器看到的页面和 API 都使用同一个域名、协议和端口，因此它们同源。服务器内部的两个应用分别监听 3000 和 8000，Nginx 统一对外提供入口。

Next.js 自身也配置了 `/api` 转发，目标默认是 `http://127.0.0.1:8000`。本次生产 Nginx 会先处理 `/api/`，所以公网 API 直接进入后端。通过 `127.0.0.1:3000/api/health` 检查时，则会经过 Next.js 的转发。项目配置见 `project/frontend/next.config.mjs`。

### 播放视频

```text
浏览器 → Nginx → FastAPI → AniCh / 稀饭接口
浏览器 ← JSON 中的播放候选与临时地址
浏览器中的 video / HLS 播放器 → 视频 CDN
```

应用服务器负责资料、来源解析、账号和观看记录。当前正式播放器会直接请求视频 CDN，实际加载速度同时涉及用户到香港服务器、香港服务器到上游接口、用户到视频 CDN 这几段网络。

观察播放页的 Network，可以分别找到应用接口请求与视频分片或 MP4 请求。健康接口成功确认应用链路可达，实际视频播放还要观察来源解析和媒体请求。

### 后端线上配置

下面是本次后端 `.env` 的关键项。

```dotenv
TSUKIMI_DATABASE=/opt/tsukimi/data/tsukimi.db
TSUKIMI_ALLOWED_ORIGINS=https://tsukimi.cc,https://www.tsukimi.cc
TSUKIMI_COOKIE_SECURE=1
```

- `TSUKIMI_DATABASE` 固定线上数据位置。日常拉取源码和重新构建后，应用仍通过这个路径打开数据库。

本次数据目录设置为 0700，后端 `.env` 设置为 0600，均归 tsukimi 用户管理。环境变量在进程启动时进入运行环境，调整配置后通过重启相应服务加载。

## E 三层部署配置怎样配合

### E1 systemd 持续管理应用进程

后端服务配置如下，与本次实操对应。

```ini
[Unit]
Description=Tsukimi FastAPI backend
After=network.target

[Service]
Type=simple
User=tsukimi
Group=tsukimi
WorkingDirectory=/opt/tsukimi/project/backend
EnvironmentFile=/opt/tsukimi/project/backend/.env
Environment=PYTHONUNBUFFERED=1
ExecStart=/opt/tsukimi/project/backend/.venv/bin/python -m uvicorn main:app --host 127.0.0.1 --port 8000
Restart=on-failure
RestartSec=3
UMask=0077

[Install]
WantedBy=multi-user.target
```

前端服务的应用部分如下，其完整定义可在服务器用 `systemctl cat tsukimi-frontend` 查看。

```ini
[Unit]
Description=Tsukimi Next.js frontend
After=network.target tsukimi-backend.service

[Service]
Type=simple
User=tsukimi
Group=tsukimi
WorkingDirectory=/opt/tsukimi/project/frontend
Environment=NODE_ENV=production
ExecStart=/usr/bin/npm run start
Restart=on-failure
RestartSec=3
UMask=0077

[Install]
WantedBy=multi-user.target
```

`User` 指定运行身份，`WorkingDirectory` 指定启动目录，`EnvironmentFile` 为后端提供环境配置，`ExecStart` 指定启动命令。`Restart=on-failure` 会在异常退出时尝试重启。`After` 声明启动先后顺序，应用的就绪状态继续通过健康请求核对。[Ubuntu 24.04 的 systemd 服务说明](https://manpages.ubuntu.com/manpages/noble/man5/systemd.service.5.html)

| 命令 | 本次应理解的作用 |
| --- | --- |
| `systemctl daemon-reload` | systemd 重新读取修改后的服务定义 |
| `systemctl enable --now 服务名` | 设置开机启动，同时立即启动服务 |
| `systemctl start 服务名` | 启动当前已停止的服务 |
| `systemctl restart 服务名` | 让应用进程重新启动并读取代码和环境配置 |
| `systemctl status 服务名 --no-pager` | 查看进程状态及最近日志 |
| `journalctl -u 服务名 -n 50 --no-pager` | 查看指定服务最近 50 条日志 |

本次首次启动后分别检查了 8000 的后端健康接口、3000 的 API 转发，以及 3000 的首页响应。关闭 SSH 后，进程继续由 systemd 管理。

### E2 Nginx 把公网请求交给应用

下面是申请证书前使用的 HTTP 配置，用于回顾路径转发。HTTPS 配好后的当前文件还包含 443 入口及证书配置，可以通过 `nginx -T` 查看实际生效内容。

```nginx
server {
    listen 80;
    server_name tsukimi.cc www.tsukimi.cc;

    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Connection "";
    proxy_buffering off;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
    }
}
```

`server_name` 选择域名对应的网站，`location` 按路径选择服务。这里 `proxy_pass` 保留请求 URI，所以 `/api/health` 到后端时仍是 `/api/health`。转发头携带原域名、访问者 IP 和公网协议。[Nginx 代理模块说明](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

`proxy_buffering off` 允许上游响应及时传给浏览器，配合 Next.js 的流式响应。配置完成后，通过 `nginx -t` 检查语法，再用 `systemctl reload nginx` 加载网站配置。[Next.js 流式响应与反向代理](https://nextjs.org/docs/app/guides/self-hosting#streaming-and-suspense)

本次使用 shell 的 `<<'EOF'` 写配置，带引号的结束标记会让 `$host`、`$scheme` 等内容原样保存到文件。结束行 `EOF` 单独占一行。这也是复制配置时需要保留引号和换行的原因。

### E3 域名、防火墙、HTTPS

| 设置 | 本次值 | 可以观察什么 |
| --- | --- | --- |
| A 记录 `@` | `119.28.30.106` | `tsukimi.cc` 找到服务器 |
| A 记录 `www` | `119.28.30.106` | `www.tsukimi.cc` 找到同一服务器 |

| 系统 UFW | 截图显示 inactive | 本次系统 UFW 状态已核对 |

| `certbot.timer` | 已启用 | 后续定期尝试续期 |

A 记录负责域名到 IPv4 地址的解析，`@` 对应根域名，`www` 对应子域名。[DNSPod 的 A 记录说明](https://docs.dnspod.com/dns/help-a/)

首次证书操作在服务器 root 终端完成。

```bash
apt-get install -y certbot python3-certbot-nginx
certbot --nginx -d tsukimi.cc -d www.tsukimi.cc --redirect
systemctl enable --now certbot.timer
certbot renew --dry-run
```

Certbot 通过域名验证取得证书，再为 Nginx 安装 HTTPS 配置。`--redirect` 配置 HTTP 到 HTTPS 的跳转。`--dry-run` 使用测试流程演练续期，定时器负责后续调度。本次重复执行申请命令时，工具发现已有证书，你输入 `c` 取消了那次重复操作，随后公网 HTTPS 与续期演练均已通过。[Certbot 使用与自动续期说明](https://eff-certbot.readthedocs.io/en/stable/using.html#automated-renewals)

本机 PowerShell 的验收命令如下，截图中的两个健康响应均为 `{"status":"ok"}`，HTTP 首页返回 301，`Location` 指向 HTTPS。

```powershell
Resolve-DnsName tsukimi.cc -Type A
Resolve-DnsName www.tsukimi.cc -Type A
curl.exe --max-time 20 https://tsukimi.cc/api/health
curl.exe --max-time 20 https://www.tsukimi.cc/api/health
curl.exe -I --max-time 20 http://tsukimi.cc/
```

日常登录与同步验收统一使用 `https://tsukimi.cc`。当前会话 Cookie 按主机保存，根域名和 www 子域名各自建立会话，换设备时在同一域名登录相同账号，再核对账号记录。

## F 日常修改以后，怎样更新线上版本

### F1 本机提交与推送

在 Windows PowerShell 进入本机工作区。

```powershell
cd C:\Users\lx\Desktop\Tsukimi
git status

```

### F2 记录旧版本并备份数据库

日常更新前，先在服务器 root 终端记录当前版本，之后可用它定位更新前的代码。

```bash
runuser -l tsukimi -c 'cd /opt/tsukimi && git rev-parse HEAD && git status --short'
```

本次更新前代码为 `dd0eb9d`，更新目标为 `300037b`。数据库备份在应用仍运行时通过 SQLite backup 接口取得一致快照。[Python 3.12 的 SQLite backup 接口](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.backup)

下面是本次用过的备份方式，在服务器 root 终端执行，由 tsukimi 用户读写数据文件。

```bash
runuser -u tsukimi -- /opt/tsukimi/project/backend/.venv/bin/python - <<'PY'
from contextlib import closing
from datetime import datetime
from pathlib import Path
import sqlite3

source = Path("/opt/tsukimi/data/tsukimi.db")
stamp = datetime.now().strftime("%Y%m%d-%H%M%S-%f")
target = source.with_name(f"tsukimi.before-progress-update-{stamp}.db")

with closing(sqlite3.connect(f"file:{source}?mode=ro", uri=True)) as database:
    with closing(sqlite3.connect(target)) as backup:
        database.backup(backup)

target.chmod(0o600)
print("Backup created", target)
PY
```

`mode=ro` 让源文件以只读方式打开，`backup` 将快照写入带时间的独立文件。本次截图显示备份已生成，账号与观看记录可以作为更新前的数据恢复点。进一步恢复时，先保存当前数据副本并停止会写库的应用，再选定备份进行恢复，恢复后的数据对应备份时间点。完整线上恢复演练待后续安排。

### F3 服务器拉取代码

服务器 root 终端通过应用用户执行。

```bash
runuser -l tsukimi -c 'cd /opt/tsukimi && git pull --ff-only origin main && git log -1 --oneline'
```

`--ff-only` 要求更新可以快进，出现分叉时 Git 会停止，让我们先检查双方历史。本次服务器已显示 `300037b`。

此时源文件已更新，Next.js 的正式页面还要由新构建产生，正在运行的后端也需要重新启动来加载新代码。文件版本、构建版本和运行进程在发布过程中分别核对。

### F4 构建并重启

这一段会带来短暂访问中断。后续继续部署时，在服务器 root 终端执行。

```bash
systemctl stop tsukimi-frontend
runuser -l tsukimi -c 'cd /opt/tsukimi/project/frontend && npm run build'
```

构建成功并返回 shell 后，继续加载新版本。

```bash
systemctl restart tsukimi-backend
systemctl start tsukimi-frontend
```

本次沿用已安装的依赖。以后如果依赖声明或锁文件发生变化，在应用用户对应目录按新声明安装，再构建。修改 systemd 服务定义后执行 `daemon-reload` 并重启相应应用，修改 Nginx 配置后先 `nginx -t`，再 reload。

构建失败时先保留报错输出，核对代码、依赖、内存和磁盘情况。若需恢复上一版，结合记录的提交选择代码恢复方案，重新构建并验证。代码回退和数据库恢复分别按实际变更处理，具体 Git 操作见 [Git 使用约定](Git使用约定.md)。

## G 出问题时怎样缩小范围

### 从服务器内部逐层检查

以下命令在服务器 root 终端执行，逐条观察结果。

```bash
systemctl status tsukimi-backend tsukimi-frontend nginx --no-pager
curl -fsS http://127.0.0.1:8000/api/health
echo
curl -I --max-time 30 http://127.0.0.1:3000/
curl -i -sS --max-time 15 -H 'Host: tsukimi.cc' http://127.0.0.1/api/health
echo
journalctl -u tsukimi-backend -n 50 --no-pager
journalctl -u tsukimi-frontend -n 50 --no-pager
```

8000 检查后端，3000 检查前端，带 Host 的 80 端口请求检查 Nginx 域名路由。HTTPS 启用后，这条 HTTP 请求应返回跳转，命令中的 `-i` 会显示状态码与 Location。最后在 Windows 通过域名请求，核对公网路径。

| 现象 | 下一项观察 |
| --- | --- |
| 域名解析结果与服务器 IP 不同 | 用 `Resolve-DnsName` 核对 A 记录，检查 DNS 配置与缓存 |
| 服务器内可访问，电脑访问超时 | 核对腾讯云入站规则、系统防火墙与公网端口 |
| Nginx 返回 502 | 检查两个应用的运行状态、监听地址与 journal 日志 |
| 拉取代码后界面仍是旧效果 | 对照 Git 提交、构建是否成功、应用是否重启及浏览器刷新结果 |
| 登录或刷新后的身份异常 | 核对 HTTPS、所用域名、Cookie 请求、来源配置与账号接口响应 |
| 健康接口正常，某部番剧没有线路 | 观察播放接口的来源匹配和上游响应，再看视频 CDN 请求 |
| 某条线路播放慢 | 分别比较来源解析耗时与浏览器媒体请求的耗时 |
| 证书续期异常 | 查看 `certbot.timer`、续期演练输出及域名公网访问情况 |

### 命令与配置要配套看

```bash
systemctl cat tsukimi-backend
systemctl cat tsukimi-frontend
nginx -t
systemctl list-timers --all certbot.timer
certbot certificates
```

`systemctl cat` 帮助核对运行用户、路径和启动命令。`nginx -t` 检查配置语法。`certbot certificates` 显示证书覆盖的域名及到期信息。服务显示 active 后，继续通过请求和页面操作观察应用是否就绪。
