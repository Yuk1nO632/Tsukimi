# 07：联网资料、追番片单与放送日历

日期：2026-10-27。本轮沿用 React/Next.js、FastAPI、SQLite，不引入账号系统或新数据库。新增运行依赖为零，仍使用原来的两个终端启动方式。

先完成 A 和 B 就可以停下来交流，不需要一次读完所有新增文件。下面区分了工具验证与个人复习；工具通过不代表你已独立掌握。

## A. 先搜索一部原片库之外的动画

1. 打开首页，在顶部搜索“命运石之门”，也可以试别名“石头门”。
2. 搜索会进入 /search?q=…，结果不再只包含本地九部。核对本篇、续作与短篇，打开 2011 年的《命运石之门》。
3. 观察详情中的简介、原名、集数、评分人数、排名和制作信息。
4. 展开浏览器 Network，找到 GET /api/catalog?q=…，查看请求参数和响应中的 items、total、page。
5. 到详情页的“播放来源”搜索稀饭作品，核对年份与集数后手动选择。选择不会自动猜季数；作品名完全相同的候选仅排在前面。
6. 点击播放，观察网址 source 参数。资料 ID、稀饭作品 ID、稀饭剧集 ID 的区别仍沿用第 06 节。

两条数据流保持分开：

```text
番剧资料：浏览器 /api/catalog → FastAPI catalog.py → Bangumi → 统一 JSON → React 卡片
播放资源：详情中人工选来源 → /watch → /api/playback → 稀饭 → 临时视频地址 → video
```

详情页是 Next.js 服务端读取资料，浏览器 Network 不一定会有独立的 /api/catalog/{id} 请求。可以在后端 /docs 中手动查看该接口；本次先理解浏览器发起的搜索请求即可，不要求一次学完服务端渲染。

## B. 再改一次追番状态

1. 在番剧详情选择“想看”，打开独立的 /collection 页面。
2. 改成“在看”，刷新浏览器，检查状态仍在。
3. 改成“看完”，检查分组计数和筛选结果同步变化。
4. 在片单里搜索片名、切换排序；最后试一次取消收藏，确认条目移出所有分组。
5. Network 中找到 PUT /api/collection/{anime_id}。请求体的 status 是 wish、watching 或 completed。

```text
选择状态 → PUT + JSON → FastAPI 校验会话和状态
  → SQLite 提交 → 返回整份片单 JSON
  → CollectionProvider 更新 collectionItems → 计数、卡片和选择框同步
```

失败时不提前改变已确认状态；如果服务端可能已处理但浏览器没收到响应，可重新读取片单确认结果。

旧收藏使用同一张 favorites 表，新增 status 和 updated_at 列。旧记录默认“想看”，没有清空数据库或另起身份机制。catalog_cache 保存公开番剧资料快照，使片单在重启后仍能显示原来搜到的新条目。这里保存的是番剧资料，不是临时视频地址。

旧 /api/favorites 仍兼容，当前界面改用返回完整条目和状态的 /api/collection。旧版 collection-api.js 和 home-library.jsx 已被新模块替代；前一阶段的完整代码仍可从 Git 的 95cf849 / 413179f 查看。

## C. 理解两种筛选的位置

番剧索引 /browse 的年份、季度、类型、排序和分页会写进 URL，并由后端向 Bangumi 查询，不是只对当前一页卡片做筛选。选择季度而未选择年份时，按当前年查询；排序提供综合匹配、收藏热度、评分和排名。收藏热度是 Bangumi 的收藏人数，不是 Tsukimi 的访问量。

放送日历 /calendar 从 Bangumi 的当前放送表读取整个星期。切星期、输入片名和“只看我的追番”是在已取得的本周数据中筛选，不需要每按一次星期都请求上游。

日历展示放送安排，不把原始首播日期重新包装成今天更新，也不保证来源站已上架某一集。只有进一步接入来源更新记录，才能可靠显示“已更新至第几集”。首页的本季分区按北京时间的当前年份与季度查询，经典回看仍使用保留的本地精选资料。

## D. 建议的代码阅读顺序

第一次只读前四项，顺着一个请求看：

1. frontend/components/site-header.jsx：顶部搜索怎样跳到 /search?q=…。
2. frontend/components/catalog-browser.jsx 与 lib/use-api.js：读取 URL 条件、请求数据、显示加载/失败/空结果。
3. backend/catalog.py 的 create_catalog_router、search、normalize：接收条件、请求资料站、统一字段。
4. frontend/components/collection-provider.jsx：后端成功响应后，怎样替换共享 state。
5. backend/main.py 的 collection 接口与 database.py：会话校验、状态保存、旧表迁移。
6. frontend/components/detail-view.jsx：详情、片单状态和来源选择。
7. frontend/components/calendar-board.jsx 与 home-dashboard.jsx：已有数据怎样组合成页面。

资料缓存、锁和缓存失效属于后续可读内容。本轮先不要求手写或背下这些实现。

## 本轮边界

- 仍是匿名浏览器片单，没有账号与跨设备同步；Cookie 规则沿用第 05 节。
- 有“在看”状态，不代表已保存播放到第几分钟。观看进度、继续观看和自动连播仍未实现。
- 来源匹配保存在页面网址中，不自动记成用户的永久来源偏好。
- 资料查询有超时和重试；搜索/日历上游响应缓存约 10 分钟，详情快照约 24 小时。详情服务不可用时可以显示带提示的已缓存资料。
- 旧数据库迁移前已保存本机备份到 .cache/tsukimi-before-portal-20261027.db；该文件与运行数据库均不提交 Git。
- 默认前端使用 3000、后端 8000。TSUKIMI_API_ORIGIN 供自定义后端入口使用；修改后要重启前端，生产模式需重新构建。TSUKIMI_BUILD_DIR 仅用于隔离验证输出，正常运行不用配置。
